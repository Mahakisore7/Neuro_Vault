Why PostgreSQL, not Neo4j

Short answer: stay on PostgreSQL and finish the graph feature with a recursive CTE, as originally designed. Switching to a native graph database would cost more than it buys — not because Neo4j is a bad tool, but because this project's actual access pattern doesn't need what Neo4j is good at.

01The one question that actually decides this

Not "does the app have a graph in it?" — almost every app does, somewhere. The question a real engineering team asks is:

Is multi-hop traversal the primary, high-volume access pattern, at a scale where an index-free-adjacency engine's advantage actually shows up? That's the test. Social graphs, fraud-ring detection, and recommendation over hundreds of millions of edges pass it decisively. A personal notes app with a graph of a few thousand edges, bounded to five hops, does not.

NeuroVault's own knowledge graph — knowledge_links, a self-referencing many-to-many table on notes — is exactly the second case. One relationship among fifteen tables, not the whole storage model.

02Nobody in this exact product category uses a graph database

This isn't a hunch — it's checkable, and every comparable product lands the same way:

ProductWhat it actually runs on
NotionSharded PostgreSQL — by far the largest product here, publicly documented on their own engineering blog.
Obsidian, LogSeqNo server database at all — local-first; the graph view is recomputed from Markdown files on open.
Roam ResearchDatomic — a Datalog store, not a property-graph engine like Neo4j.

Every one of them treats "notes connect to notes" as one relationship inside a conventional product, not as a reason to adopt graph-native storage. That's the exact shape of this project.

03The traversal query already exists — it isn't hand-waved

This is the point worth making concretely: the "hard part" people assume needs a graph database is already fully designed as ordinary SQL, in docs/phases/New/03-SQL-LAYER.md — not invented for this conversation.

WITH RECURSIVE connected_graph AS ( -- anchor: the starting note, depth 0 SELECT n.id, n.title, 0 AS depth, ARRAY[n.id] AS visited_path FROM notes n WHERE n.id = :root_id UNION ALL -- recursive term: everything one hop from what we already have SELECT nxt.id, nxt.title, g.depth + 1, g.visited_path || nxt.id FROM connected_graph g JOIN knowledge_links kl ON kl.source_note_id = g.id OR kl.target_note_id = g.id JOIN notes nxt ON nxt.id = CASE WHEN kl.source_note_id = g.id THEN kl.target_note_id ELSE kl.source_note_id END WHERE g.depth < :max_depth -- bound the work AND nxt.id <> ALL(g.visited_path) -- never revisit: prevents cycles ) SELECT DISTINCT ON (id) id, title, depth FROM connected_graph ORDER BY id, depth;

The exact query from the design doc, condensed. It's iterative, not recursive-call-stack recursion — Postgres runs the anchor once, then re-runs the recursive term only against the newest rows each pass, until nothing new appears.

Two lines are doing the safety work an engineer would ask about first: depth < :max_depth bounds the traversal, and nxt.id <> ALL(visited_path) stops it from looping forever around a cycle. That's the entire cycle-safety story — no different in kind from what a graph database gives you for free, just written out instead of hidden in the engine.

04What a full migration would actually delete

This is the part worth being explicit about, because it's easy to lose sight of while focused on the graph feature alone: Neo4j has no equivalent for most of what's currently working and defensible in this project.

Composite-FK tenancy

Every ownership rule (ADR-001) is enforced by a two-column foreign key. Neo4j has no foreign keys, composite or otherwise — ownership goes back to being an application-level if statement, the exact failure mode this design exists to remove.

Generated columns

word_count and search_vector are computed and stored by Postgres on every write. No equivalent in a schemaless graph store — that logic moves back into application code, where it can drift out of sync.

CHECK constraints & RLS

Slug formats, color hex codes, SM-2 bounds, row-level security — all enforced by the database itself, regardless of what wrote the row. None of it transfers.

Trigger-driven history

Version history and rollback exist because a BEFORE UPDATE trigger and a stored procedure guarantee it, in the same transaction as the edit. Cypher has no comparable trigger mechanism — this logic would move to the application too.

None of that is a reason graph databases are bad — it's a reason this particular project's strongest, most gradeable material is relational, not graph work, and a migration would trade it away for a feature that's one table out of fifteen.

05The actual industry-standard answer, stated honestly

The real pattern used in industry isn't "pick one database forever" — it's polyglot persistence: keep the system of record wherever integrity guarantees matter most, and add a specialized store only once a specific, measured need justifies the operational cost of running two databases in sync.

True today recommended

PostgreSQL is the system of record for everything, including the graph. One database, one transaction boundary, one thing to back up and operate. Correct for thousands of edges at bounded depth.

Would become true if...

...the graph grew into millions of edges with unpredictable-depth queries as the primary feature, or needed graph-native algorithms (PageRank-style ranking, community detection) that recursive SQL genuinely struggles with. Then: add Neo4j as a derived read-store, synced from Postgres — never replace Postgres outright.

Why not build the hybrid now, just to be safe? A second database means a sync pipeline, eventual-consistency risk, and twice the operational surface — real, ongoing cost — to serve a graph that doesn't yet exist in the product at all. Paying that cost before the simpler version has even shipped once is the mistake, not the caution.
"I looked at Neo4j, and here's the specific access-pattern reasoning for why I stayed on PostgreSQL" is a stronger answer in a database-systems review than switching on request without that analysis — it's the same judgment a real engineering team is expected to show before adopting a new datastore.
