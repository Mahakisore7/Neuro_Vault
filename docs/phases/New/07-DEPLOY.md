# Phase 7 — Deployment

**Goal:** a public URL both teammates and an examiner can use, with production
configuration that differs from development deliberately rather than accidentally.

**Time:** ~3 hours · **Prerequisite:** [`06-QUALITY.md`](06-QUALITY.md)

**Done when:** the full flow works on a public URL, from a phone, on mobile data.

## 7.1 The topology

```
Browser
   │
   ├──► Render Static Site      neurovault.onrender.com
   │       out/ from `pnpm build`  — HTML/CSS/JS, no server (ADR-010)
   │
   ├──► Render Web Service      neurovault-api.onrender.com
   │       Docker `runtime` stage — FastAPI
   │
   ├──► Supabase                Auth (token issuance) + Storage
   │
   └──► (backend only) ────────► Supabase PostgreSQL
                                 Upstash Redis
                                 Sentry
```

Three managed services, one Docker image, no servers to patch.

## 7.2 Promote the schema to Supabase

Development ran against local PostgreSQL ([ADR-012](00-ARCHITECTURE.md#adr-012)). The
production database has never seen a migration. Apply them **before** the API deploys.

```bash
cd backend

# Session pooler on port 5432 — NOT 6543. See §1.4 for why this matters.
export DATABASE_URL="postgresql+asyncpg://postgres.PROJECT:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres"
export DATABASE_URL_SYNC="postgresql://postgres.PROJECT:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres"

# Read the SQL before it touches the production database.
uv run alembic upgrade head --sql > /tmp/production-migration.sql
less /tmp/production-migration.sql

uv run alembic upgrade head
uv run alembic current            # confirm the head revision
```

**`--sql` is offline mode.** It prints the SQL instead of executing it — the reason
`run_migrations_offline()` exists in `env.py` (§1.10). Reading the statements once,
before the first production migration, costs two minutes and is how you notice that an
autogenerated migration contains a `DROP TABLE` you did not intend.

Then verify in the Supabase SQL editor:

```sql
\dt   -- 15 tables + alembic_version
\dv   -- 4 views
\df   -- 6 routines
\di   -- 10 indexes
SELECT tablename, rowsecurity FROM pg_tables
WHERE schemaname = 'public' ORDER BY tablename;
-- rowsecurity must be true for all 15
```

**That last query is the one to actually run.** RLS enabled on 14 of 15 tables is a data
leak with no symptom.

### Seed the lookup table

`relationship_types` is a fixed vocabulary, not user data. Production needs it:

```bash
uv run python -c "
import asyncio
from scripts.seed import seed_relationship_types
asyncio.run(seed_relationship_types())
"
```

Factor `seed_relationship_types()` out of `scripts/seed.py` so production gets the seven
types without the demo user, workspace, and notes.

## 7.3 Backend on Render

**New → Web Service → connect the repository.**

| Setting | Value |
|---|---|
| Root Directory | `backend` |
| Runtime | Docker |
| Dockerfile Path | `./Dockerfile` |
| Docker Build Target | `runtime` |
| Health Check Path | `/health` |
| Instance Type | Free (spins down after 15 min idle) |

**`runtime`, not `dev`.** The `dev` stage runs `--reload`, installs dev dependencies, and
runs as root. Naming the target explicitly is what makes the multi-stage Dockerfile
worth having.

**Environment variables** — set in the Render dashboard, never in a file:

```
DATABASE_URL         postgresql+asyncpg://…pooler.supabase.com:5432/postgres
DATABASE_URL_SYNC    postgresql://…pooler.supabase.com:5432/postgres
SUPABASE_URL         https://PROJECT.supabase.co
SUPABASE_ANON_KEY    eyJ…
SUPABASE_SERVICE_ROLE_KEY  eyJ…
SUPABASE_JWT_SECRET  …
REDIS_URL            rediss://default:…@….upstash.io:6379
SENTRY_DSN           https://…@sentry.io/…
ENVIRONMENT          production
DEBUG                false
ALLOWED_ORIGINS      https://neurovault.onrender.com
GRAPH_MAX_DEPTH      3
GRAPH_CACHE_TTL      300
```

> **`ALLOWED_ORIGINS` is the variable that broke the previous deployment.** It is set
> here, in production, which is exactly the path the old `list[str]` declaration
> crashed on — and exactly the path CI never exercised. The `NoDecode` fix (§1.6,
> [ADR-005](00-ARCHITECTURE.md#adr-005)) is what makes this line safe, and backend CI
> now sets it too so the parsing path is tested on every push.

**`ENVIRONMENT=production` is load-bearing.** `_production_safety` in `config.py`
refuses to start with `DEBUG=true` or a wildcard origin. A misconfigured deploy fails at
boot, loudly, instead of serving stack traces to strangers.

### Pre-deploy migrations

Render **Settings → Pre-Deploy Command**:

```
uv run alembic upgrade head
```

This runs after the build and before traffic shifts. If it fails, the deploy aborts and
the previous version keeps serving — which is the behaviour you want, and it is why
migrations belong here rather than in the container's start command. A start-command
migration runs on *every* instance restart, and two instances starting together race.

## 7.4 Frontend on Render

**New → Static Site.**

| Setting | Value |
|---|---|
| Root Directory | `frontend` |
| Build Command | `corepack enable && pnpm install --frozen-lockfile && pnpm build` |
| Publish Directory | `out` |

**Environment variables** (build-time — see §1.8):

```
NEXT_PUBLIC_SUPABASE_URL       https://PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY  eyJ…
NEXT_PUBLIC_API_URL            https://neurovault-api.onrender.com
```

**SPA rewrite** — Render **Redirects/Rewrites**:

| Source | Destination | Action |
|---|---|---|
| `/*` | `/index.html` | Rewrite |

Without it, a hard refresh on `/notes/abc-123` returns 404: the file does not exist on
disk, because client-side routing invented that path. The rewrite serves the shell and
lets the router resolve it.

## 7.5 Supabase configuration

**Authentication → URL Configuration:**

```
Site URL       https://neurovault.onrender.com
Redirect URLs  https://neurovault.onrender.com/**
               http://localhost:3000/**
```

Both entries are needed — the production one for real users, localhost so you can still
develop. Missing the production URL means email-confirmation links redirect to
`localhost:3000` on the user's machine and appear broken.

**Storage → New Bucket → `resources`, private.** Then policies so a user can only touch
their own folder:

```sql
CREATE POLICY "own folder upload" ON storage.objects
  FOR INSERT TO authenticated
  WITH CHECK (bucket_id = 'resources'
              AND (storage.foldername(name))[1] = auth.uid()::text);

CREATE POLICY "own folder read" ON storage.objects
  FOR SELECT TO authenticated
  USING (bucket_id = 'resources'
         AND (storage.foldername(name))[1] = auth.uid()::text);
```

Uploads go **browser → Supabase Storage directly**, never through FastAPI. The file
bytes do not transit our API, so there is no request-size limit to raise, no memory
spike on the free instance, and no upload endpoint to secure. The backend only ever
stores the resulting URL.

## 7.6 The seven differences between development and production

State these in the viva. "It's the same, but deployed" is the wrong answer.

| # | Development | Production | Why |
|---|---|---|---|
| 1 | `DEBUG=true` | `DEBUG=false` | Stack traces contain SQL and connection strings |
| 2 | `/docs` open | `/docs` disabled | Do not publish your attack surface |
| 3 | `ALLOWED_ORIGINS=localhost:3000` | the real domain | CORS is a real boundary |
| 4 | Local PostgreSQL | Supabase session pooler | ADR-012 |
| 5 | `echo=True` — every query logged | silent | Log volume, and queries contain user data |
| 6 | Docker `dev` target, root, `--reload` | `runtime` target, non-root | Attack surface |
| 7 | No Sentry | Sentry with `send_default_pii=False` | Errors you never see are errors you never fix |

Items 1, 2, 3, and 5 are enforced by `config.py` reading `ENVIRONMENT`, not by a
checklist. Item 6 is enforced by the Render build target. **Configuration that depends
on someone remembering is configuration that will eventually be wrong.**

## 7.7 The free tier, and what to say about it

Render's free web service **spins down after 15 minutes of inactivity**. The next
request takes 30–50 seconds while the container cold-starts.

This will happen during your demo if you do not plan for it.

- **Open the app five minutes before you present.** One request wakes it.
- If asked: *"The free instance cold-starts after idling. In production you'd pay for an
  always-on instance, or put a scheduled ping in front of it. The trade-off is explicit
  and it's a cost decision, not a design one."*

Supabase's free tier **pauses a project after 7 days of no activity**. Log in once a
week in the run-up to submission.

## 7.8 Verify the deployment

```bash
API=https://neurovault-api.onrender.com

curl -fsS $API/health                          # {"status":"ok",...}
curl -s -o /dev/null -w "%{http_code}\n" $API/docs   # 404 — disabled in production
curl -s -o /dev/null -w "%{http_code}\n" $API/api/v1/notes   # 401 — no token

# CORS: the real origin is allowed…
curl -s -D- -o /dev/null -X OPTIONS $API/api/v1/notes \
  -H "Origin: https://neurovault.onrender.com" \
  -H "Access-Control-Request-Method: GET" | grep -i access-control-allow-origin

# …and an arbitrary one is not.
curl -s -D- -o /dev/null -X OPTIONS $API/api/v1/notes \
  -H "Origin: https://evil.example.com" \
  -H "Access-Control-Request-Method: GET" | grep -i access-control-allow-origin
# (no header ⇒ the browser will block it)
```

Then, in a browser, on a phone, on mobile data — not on your laptop's network:

```
□ Sign up → confirmation email arrives → link returns to the PRODUCTION domain
□ Log in
□ Create a note, edit it, see "Saved — version created"
□ Version history populates; rollback works
□ Link two notes; the graph renders; the depth slider changes the node count
□ Search returns ranked, highlighted results
□ Upload a PDF resource; it appears; another account cannot fetch its URL
□ Sign out; a direct visit to /dashboard redirects to /login
```
