01 — Premise

Why a graph, and why that makes it a DBMS project

Most note apps give you two structures. NeuroVault's schema models a third — and that one choice is what pulls real database machinery into the design.

The two everyone has

  • A hierarchy — workspace → notebook → note. A tree.
  • A set — tags. Unordered labels.

The third one

  • A graph — "Linear Algebra is a prerequisite of Machine Learning, strength 9." A typed, directed, weighted edge between any two notes.

What that forces into the schema

  • A self-referencing many-to-many junction — two foreign keys on one table, both pointing back at notes.
  • Recursive traversal — "everything within N hops" is one query, not a loop in application code.
  • An asymmetric security model expressed as two different foreign-key shapes rather than an if statement.
The claim I want to defend: the interesting work here is in the schema, not the screens. Ownership rules, history, and integrity are enforced by PostgreSQL itself — so they hold even if every line of application code were bypassed.

03 — Architecture

How the pieces fit

Why identity is split out

Supabase Auth owns password hashing, OAuth redirects and token refresh — all easy to get subtly wrong by hand. FastAPI owns the domain: authorization rules and the graph queries. The JWT is the handoff. FastAPI never sees a password; Supabase never sees a note.

The layering rule

Routes never touch SQLAlchemy; services never import FastAPI. Every arrow points down exactly one layer. That's what makes each layer testable in isolation — and it's checkable mechanically, by grepping for sqlalchemy under the routes directory and expecting zero hits.

06 — Schema · key decision

Tenancy enforced by composite foreign keys

The single design idea I'd most want to be asked about. Every child table that belongs to a user carries the owner's id and puts it inside the foreign key.

The usual way

-- FK asks only: does the parent exist? FOREIGN KEY (workspace_id) REFERENCES workspaces(id)

Then application code must remember, on every single write path, to also check that the workspace belongs to the caller. Miss it once and you have a cross-tenant write.

What NeuroVault does

-- FK asks: does the parent exist -- AND belong to this exact user? FOREIGN KEY (workspace_id, owner_id) REFERENCES workspaces(id, owner_id) ON DELETE CASCADE

Filing a notebook under someone else's workspace isn't a bug to be caught — it is a row PostgreSQL physically cannot store, from the app, a script, or psql.

The cost, stated plainly

notebooks.owner_id is derivable through workspace_id → workspaces.owner_id, so storing it again is a deliberate 3NF violation. The redundancy is safe precisely because the composite FK is what enforces it: the two copies cannot disagree, because a row where they disagree cannot exist. A denormalisation whose consistency is guaranteed by the same constraint that motivates it.

Prerequisite that's easy to miss: a two-column foreign key needs a two-column unique constraint to point at. Every parent table carries an extra UNIQUE (id, owner_id) that exists only to be a composite-FK target — visible as uq_workspaces_id_owner_id and friends in the live schema.

07 — Schema · the graph

One table, two foreign keys, deliberately different

knowledge_links is a self-referencing many-to-many junction on notes. The asymmetry between its two sides is the security model.

Read it as a sentence

"You may draw a connection from a note you own to any note you can read — including someone else's public one — and never the reverse."

That whole paragraph of policy is two lines of DDL. No service-layer check can be forgotten, because there is no service-layer check.

Supporting constraints

  • CHECK (source_note_id <> target_note_id) — no self-links.
  • UNIQUE (source, target, rel_type_id) — the same relationship can't be recorded twice.
  • rel_type_id uses ON DELETE RESTRICT — a relationship type in use cannot be deleted out from under its edges.
  • origin records whether a row came from a manual action or auto-linking, so automatic reconciliation can only ever touch rows it created.

08 — SQL layer

Generated columns — data that maintains itself Live

Two columns on notes that no application code ever writes. PostgreSQL computes and stores them on every insert and update.

word_count integer GENERATED ALWAYS AS ( -- strip HTML tags, split on whitespace, count array_length(regexp_split_to_array(btrim(regexp_replace( COALESCE(content,''), '<[^>]+>', ' ', 'g')), '\s+'), 1) ) STORED search_vector tsvector GENERATED ALWAYS AS ( setweight(to_tsvector('english', COALESCE(title,'')), 'A') || setweight(to_tsvector('english', COALESCE(body_text,'')),'B') ) STORED

Why this beats application code

  • They cannot go stale — there is no write path that updates content without recomputing them, because it's the same statement.
  • They cannot be wrong — PostgreSQL rejects any direct write to a generated column.
  • Title matches outrank body matches by construction: setweight 'A' vs 'B'.

One subtlety worth knowing

The two-argument to_tsvector('english', …) form is mandatory. The one-argument form reads a session setting, which makes it STABLE rather than IMMUTABLE — and PostgreSQL only permits IMMUTABLE expressions in a generated column. The single-argument version fails at migration time with an error that doesn't obviously say why.

Honest status: search_vector is computed and stored on every write today, but the GIN index over it hasn't been created and nothing queries it yet. Search is the nearest unbuilt feature — the expensive half is already done.

09 — SQL layer

Trigger-driven version history Live

No application code inserts into note_versions. Ever. History exists because of what PostgreSQL does inside the same UPDATE statement that changes the note.

Design points

  • BEFORE UPDATE, snapshotting OLD — the point is to preserve the state before this edit. Using NEW would make version 1 permanently unreachable.
  • IS DISTINCT FROM, not <> — NULL-safe, so a note that has never had content doesn't produce spurious versions.
  • Pinning a note or toggling is_public writes no version — only title and content changes count as edits.

Why the version number can't race

The trigger computes MAX(version_num) + 1, which looks like a classic read-modify-write race. It isn't: the UPDATE that fired the trigger already holds a row-level exclusive lock on that note, so two concurrent edits to the same note serialise. Edits to different notes don't contend at all.

10 — SQL layer

Rollback as a stored procedure Live

Why a procedure, not application code

  • It performs a self-contained unit of work with no return value — the textbook case for PROCEDURE over FUNCTION.
  • It re-checks ownership itself, raising with a specific ERRCODE if the caller doesn't own the note. Defence in depth: it can be CALLed directly from psql, bypassing the API entirely.
  • It keeps the restore in one round trip instead of read-then-write from Python.

The elegant part

The procedure restores content with an ordinary UPDATE — which fires the versioning trigger from the previous slide. So the state being replaced is itself versioned on the way out.

A rollback is never destructive. Restoring v1 over v3 creates v4 containing what v3 said. You can always roll back a rollback — the history is append-only by construction, not by policy.
CALL sp_rollback_note_version(p_note_id, p_version_num, p_actor_id); -- inside: ownership re-check, then UPDATE notes SET title = v.title, content = v.content WHERE id = p_note_id; -- ^ this line re-fires trg_notes_create_version

Verified end to end: create a note, edit it twice, list versions (returns [2, 1], newest first), roll back to v1, confirm the content restored, confirm the rollback produced v3, then confirm a rollback to a nonexistent version and a rollback by a different user are both rejected.

11 — Schema · integrity

Referential actions chosen per relationship

Not one blanket policy. Each foreign key answers its own question: does the child exist because of the parent, or does it merely mention it?

RelationshipActionReasoning
workspaces.owner_id → usersCASCADEA workspace exists only because its owner does. Delete the account, the workspace goes.
note_versions.note_id → notesCASCADEHistory of a note that no longer exists is meaningless.
note_versions.edited_by → usersSET NULLDeleting a user must not erase the edit history of notes they touched. The version survives; it loses its author.
activity_logs.user_id → usersSET NULLAn audit trail that disappears when the actor is deleted is not an audit trail.
knowledge_links.rel_type_idRESTRICTA relationship type still in use cannot be deleted — the edges would lose their meaning.
notes.(notebook_id, creator_id)SET NULL (notebook_id)The interesting one — see below.

The column-list SET NULL

Deleting a notebook should un-file its notes, not destroy them. But the foreign key is composite — (notebook_id, creator_id) — and a plain ON DELETE SET NULL nulls every column the key covers, including creator_id, which is NOT NULL. That delete would fail the first time anyone tried it.

ON DELETE SET NULL (notebook_id) -- PostgreSQL 15+: name the column
Where this leaked into the product: the database handled it correctly from day one — notes survived a notebook delete, unfiled. But nothing in the interface could find them again afterwards. Safe in the database, invisible to the user. That gap is why the "Unfiled" screen exists; it was built specifically to close it.

13 — UML

Class diagram — the domain model

The same 15 entities as UML classes. The arrowheads carry meaning: they're chosen from the referential actions on slide 11, not picked for looks.

Filled diamond = composition → ON DELETE CASCADE, the child cannot outlive the parent.  ·  Hollow diamond = aggregation → ON DELETE SET NULL, the child survives and loses the reference.  ·  Plain arrow = association → RESTRICT, or a junction row jointly owned by two parents.

Why KnowledgeLink uses plain associations and not composition: a link row is deleted if either endpoint note is deleted — both FKs cascade — so it has no single owner. UML composition means exclusive ownership, and this relationship genuinely isn't that, so it isn't drawn that way.

14 — UML

Class diagram — the application layers

A second class diagram, deliberately a different shape from the first. That one models data; this one models code — the standard UML pairing of a domain model with an architecture model.

Authorization lives in exactly one place

_assert_can_read and _assert_can_write are private to the service. Every route that touches a note goes through them — there is no second copy of the ownership rule to drift out of sync.

Read vs write is a real distinction: a public note is readable by others but its version history requires write permission, because history can expose drafts nobody chose to publish.

The exception hierarchy is genuine inheritance

Four error types extend DomainError. The application catches DomainError once and maps each subtype to a status code — 404, 403, 409, 422. One handler, four outcomes. That's the reason to use inheritance here rather than four separate handlers.

18 — Security

Authentication, and a bug worth the whole slide

How it works

  1. The browser signs in through Supabase directly — password or OAuth.
  2. Supabase returns a JWT. Its sub claim is our users.id — the same UUID, not a mapping.
  3. Every API call carries Authorization: Bearer <token>.
  4. FastAPI fetches Supabase's public signing key from its JWKS endpoint, caches it, and verifies the ES256 signature and the authenticated audience.
  5. A trigger on auth.users mirrors new accounts into public.users.

The bug, and why it matters Fixed

Every real login returned 401, while a self-signed test token verified fine. The obvious diagnosis was "the shared secret is wrong." It was checked against the dashboard — it matched byte for byte.

The real cause: Supabase had moved to asymmetric ES256 signing. The shared secret was still correct and still valid — it just wasn't what signs session tokens any more. Confirmed by fetching the JWKS endpoint and finding a published public key.

The lesson I'd offer from this: the test script signed tokens with the same secret the backend verified with. A test that signs and verifies with the same key can prove the verification logic is correct — but it can never detect that the key itself is the wrong key for the job. Only a token from the real issuer can prove that. Written up as ADR-018.

19 — Engineering process

Bugs found, and what each one taught

Kept as a written record — every one was diagnosed by running the system, not by reading it.

SymptomActual causeGeneralisable lesson
Migration failed: relation "id_user_id" already exists Two tables were given the same literal name for a UNIQUE constraint, bypassing the naming convention. PostgreSQL scopes the index behind a unique constraint schema-wide, not per table. Never hardcode a constraint name once a convention exists. (ADR-016)
Versioning trigger crashed: null value in column "id" note_versions.id had only a Python-side default, which SQLAlchemy applies when it builds the INSERT. A trigger's INSERT never passes through the ORM. Anything the database itself writes needs a server_default, not just a Python one.
TypeError: 'function' object is not subscriptable — hit twice, in two unrelated services Both classes have a method named list. Any annotation -> list[...] written after it in the same class body resolves list to the method, not the builtin. Fixed by ordering the methods rather than renaming a public API. The same latent trap exists in any class with a method named after a builtin.
Notes survived a notebook delete but were unreachable The database did the right thing; the interface had no screen that could list notes with a null notebook_id. Correct data model, incomplete product. A referential action is only finished when the state it produces is reachable by a user.
Two bugs reported that had already been fixed weeks earlier The fix was committed on a branch that was never merged. The running code never had it. Fixing a bug on a branch does not fix the bug. Four branches had drifted; they were consolidated and the workflow gap was documented.
19 Architecture Decision Records sit in docs/adr/. Each states a problem, the alternatives weighed, what was chosen, and what it costs — including the ones where the honest answer was "this is a known gap, deliberately not fixed yet, and here's why."

20 — Closing

Where this goes next

Immediate — highest value per effort

  1. Full-text search. The generated tsvector already exists and is maintained. Needs a GIN index and a ranked query using ts_rank_cd, plus a search screen. Smallest remaining gap between schema and product.
  2. The knowledge graph. The table, the constraints and the security model are live. Needs the recursive CTE with a cycle guard, an endpoint, and a canvas. This is the project's namesake feature and its strongest DBMS content.

After that

  • The four analytical views, including a dashboard view using FILTER aggregation.
  • The remaining designed indexes — partial, composite and trigram.
  • Collections and flashcards, both schema-complete.
  • Activity-log and notification triggers.

Questions I'd expect, with short answers

Why not a graph database?

The graph is one table of fifteen. Everything else — ownership, history, tags, scheduling — is relational, and PostgreSQL traverses recursively via WITH RECURSIVE. Two databases for one feature isn't a trade worth making. (ADR-011)

Isn't the denormalised owner_id a 3NF violation?

Yes, deliberately, in two places. It's safe because the composite FK that motivates it is also what guarantees the copies can never disagree.

Why put logic in triggers instead of the application?

Because history must hold even when the application is bypassed. The trigger runs inside the same transaction as the edit — there's no state where a note changed but its history didn't.

How do you know it works?

Every claim on slide 12 was queried live from the running database. The trigger has written 8 version rows during ordinary use.
